# 平板伪装（Tablet Spoof）

让**微信**和**企业微信**在手机上以平板模式登录，从而出现**扫码登录**入口。

**作用域严格限定**：只对 `com.tencent.mm` 和 `com.tencent.wework` 生效，其他任何 App 完全不受影响。

---

这个项目有**两个**实现，它们的完成度**完全不同**，请勿混淆：

| 实现 | 状态 | 说明 |
|---|---|---|
| **LSPosed 模块（APK）** | ✅ **可用，已多次验证** | **这是当前实际生效的机制**，发布资产就是这个 |
| **Magisk/Zygisk 原生模块** | ❌ **未达成** | 机械上完整，但功能上不产生效果（原因见下） |

**如果你只想要能用的东西：下载 Release 里的 APK。** 原生模块部分请当作一份技术记录，而不是可用产品。

## 使用

### 环境要求
- Android 10+（实测环境：Android 16 / SDK 36）
- 已安装 **LSPosed**（Zygisk 版即可）
- Root（Magisk / APatch / KernelSU 均可）

### 安装步骤
1. 安装 `TabletSpoof-v0.1.0.apk`
2. 在 **LSPosed 管理器**里启用本模块
3. **作用域只勾选两个**：`微信`、`企业微信`
4. **强制停止**两个 App（必须做，否则模块不生效）
5. 重新打开 → 登录页应出现平板入口

### 验证是否生效

**企业微信**登录页应出现：**「平板和手机同时登录」**
**微信**登录页应出现：**「同时在手机和平板上使用」** / **「仅在平板上使用」**

点进去即可看到**活的扫码二维码**。

### 关闭 / 卸载
在 LSPosed 管理器里关闭模块，强制停止两个 App 即可恢复原状。卸载模块同样。

## ✅ 已验证的能力（含证据）

| 项 | 证据 |
|---|---|
| 企业微信出现「平板和手机同时登录」，点进去是活二维码 | 截图 `01`、`03`；且**完成过一次真实扫码登录**（消息列表 + 服务端「登录操作通知」）|
| 微信出现平板选项 | 截图 `12`、`13`；**对照实验**：模块关闭时这两个选项不存在（`11`）|
| 只对这两个包生效 | LSPosed scope 精确两行 + 代码内 `equals` 双重闸门；QQ音乐进程内本模块映射数 = **0** |
| **不改变手机布局** | `1080x2340` / `density 440` 全程未变；只改一个布尔返回值，**不碰** `DisplayMetrics`/`xdpi`/density |
| device-agnostic | 产物内**零个**机型/尺寸常量（无 `1080`、`2340`、`440`、`MI 9`、`cepheus` 等）|

> **重要**：本项目**从不修改** `wm size` / `wm density`。
> 早期尝试过，证明**无效**（`wm` 改不了 `xdpi/ydpi`），且会扭曲用户屏幕。
> 现在的方案只改一个布尔返回值，外观完全不变。

## ❌ 未达成的部分：原生 Zygisk 模块

**目标**是让纯 Zygisk 原生 `.so` 独立实现（不依赖 LSPosed）。**没有做到。**

### 已经打通的（都是真实、可复现的）
| 项 | 状态 |
|---|---|
| Zygisk 载荷投递（加载/注册/注入） | ✅ |
| 严格白名单（2 包，子进程正确区分） | ✅ |
| `postAppSpecialize` 对两个目标触发 | ✅ |
| 延迟解析配方 | ✅ 两个 App 都拿到 `ArtMethod` 指针 |
| 布局解码（`access_flags` = `word[1]` 低 16 位） | ✅ 两个独立构建互证 |

### 但功能上不产生效果 —— 五个候选机制被逐一排除

| 机制 | 排除依据 |
|---|---|
| 屏幕 ≥8 英寸判定 | 实测 `isAndroidPad()` 与模块无关地返回 TRUE，该判定根本没失败 |
| `Leux` 缓存 / MMKV 预置 | 存储每次启动都被重写（有界 md5 对照，两次）|
| `DisplayMetrics` / xdpi 伪装 | 消费它的那个布尔值本来就是 TRUE |
| ART native-ify | 无法安全确定入口点偏移；错误写入会**静默破坏目标 App** |
| **KV `KV_ANDROID_PAD_LOGIN_TYPE_QR_CODE`** | **受控写入测试**：三个对照全通过，写入确认落盘，`getDeviceType()` 仍不变 |

### 最后一个矛盾的现状
```
qrMode (运行时，经 App 自己的读取器) = TRUE     ✅ 已验证
isAndroidPad()                       = TRUE     ✅ （进程内稳定，进程间可变）
isAndroidBox()                       = false    ✅ 已验证
=> 按反编译逻辑应返回 getDeviceType() = 131076
=> 实测始终为                    131073        ❌ 矛盾
```
**约 200 次采样中 `131076` 一次都没出现过**，而平板入口在 LSPosed 开启时确实显示。

**机制未确定，我们刻意不提出第六个猜测。**

## 三件必须说明的事

### 1. Zygisk 载荷的一个关键坑
从 zygote **dlopen** 时必须加 `-nostdlib++`，否则会静默加载失败：
```
E/zn-daemon64: Not found: 'libc++_shared.so' needed by '<module>'
```
另外需要 `-Wl,-z,max-page-size=16384`、`-fPIC -shared`、`-fvisibility=hidden`。

### 2. 状态输出通道（本项目最大的教训）
`/data/local/tmp` 权限是 `drwxrwx--x shell:shell` —— **App uid 只能穿越、不能创建文件**。

我们最初用它当状态输出通道，于是**所有 App 进程即便回调正常工作也写不出任何东西**，
被我们误读为「回调未送达」，并据此得出一连串错误结论。

**正确通道是 `args->app_data_dir`**（App 自己的数据目录可写）。

> **规则：当所有实验都指向同一个否定结论时，先怀疑仪器。**

### 3. 最便宜的实验往往留到最后
我们有一个从字节码推导、沿用**一整天**的模型，而**推翻它只需要一次「把模块关掉看看」的对照实验**。
这个实验从第一天起随时可做。**因为"机制推理"看起来比"动手对照"更有进展，它被拖到了最后。**

本项目每次**直接读系统状态**都立刻推翻一个假设，每次**推理机制**都反复出错。

## 反检测

只实现**已证明有用**的措施：
1. 不增加可被扫描的特征（不开新文件、无 logcat 输出）
2. 不做全局/框架层 hook
3. 白名单用精确 `equals`，不用前缀匹配
4. `Config.DEBUG = false`

**未做**（推测性、收益不明）：包名重命名、对 `PackageManager` 隐藏、伪装 root 状态等。

**实测**：微信、企业微信**当前均无活跃的 Xposed 检测**。
